# CARGO ONE — аудит и архитектурный план

Oct 9, 2026 · @Aknur Ovezova

## Резюме

Текущий CARGO ONE — это хорошо проработанный интерфейс и демо, а не платформа: все товары, заказы, деньги и логистика живут в браузере каждого пользователя, а сервер умеет только вход. Для новой концепции интерфейс, модели данных и формулы можно взять как основу, но бэкенд нужно строить заново.

- **Что ценно сейчас:** 22 экрана, админка, 3 языка (≈1 800 строк перевода), продуманные модели данных, прозрачная формула цены, 212 сквозных проверок, AR-примерка.
- **Главный разрыв:** нет общей базы данных и серверной бизнес-логики. Заказ, созданный одним пользователем, не видят ни поставщик, ни админ на другом устройстве; права проверяются в браузере.
- **Новая концепция = конвейер данных.** Источники в Китае → сырые снимки → нормализованный канонический товар → проверенный продавец → цена «под ключ» → логистика → витрина внутреннего маркетплейса, а тренды питают ранжирование.
- **Шесть движков — отдельные модули одного бэкенда**, а не шесть микросервисов: на старте это быстрее и дешевле, границы модулей позволят вынести их позже.
- **Самый рискованный блок — агрегация.** Парсинг 1688/Taobao нарушает их правила и неустойчив; основа должна быть на официальных API, партнёрских фидах и загрузке продавцов, парсинг — только там, где это разрешено.
- **Первая коммерческая веха (≈ 4–6 месяцев):** реальный бэкенд, каталог из одного-двух легальных источников, ручная верификация продавцов, цена с версионированными тарифами, ручная логистика с трекингом.
- **До старта нужны решения владельца:** юрлицо и платёжная схема в Китае и Туркменистане, модель маркетплейса (кто продавец по закону), и бюджет на доступ к API.

## Аудит текущего кода

Код чистый и типизированный (TypeScript без ошибок), но архитектурно это клиентский прототип: ≈ 75% логики — интерфейс, ≈ 16% — имитация сервера внутри браузера, сам сервер — 382 строки.

| Слой | Строк | Что внутри |
| --- | --- | --- |
| Экраны (`src/pages`) | 6 250 | 22 страницы + админка из 17 разделов |
| Компоненты | 2 100 | UI-кит, оболочка, карточки, CARGO LINE, баннеры |

React 19 + Tailwind 4, сборка esbuild, свой роутер; рантайм-зависимостей всего пять. Это плюс: мало внешнего кода и быстрая сборка (≈ 1 с).

### Что реально работает, а что имитация

| Функция | Состояние | Детали |
| --- | --- | --- |
| Вход, сессии, роли страниц | Реально (сервер) | scrypt, подписанные httpOnly-cookie, запрет саморегистрации админа |
| Каталог, заказы, платежи, инвойсы, карго | Имитация | `localStorage` браузера, искусственная задержка «сети» |
| Поиск | Правила | совпадение слов + регулярные выражения для категорий |
| Find по фото / ссылке, AI Buyer | Имитация | «сходство 98%» считается из имени файла и хэша, не из изображения |
| Цена «под ключ» | Формула, фикс. ставки | один курс, одна пошлина 10%, один тариф 28 TMT/кг |
| Рейтинг поставщика (CARGO ONE Score) | Статично | числа заданы в сиде, не вычисляются |
| «Популярно в Туркменистане» | Случайное число | `popularityAshgabat` из генератора в сиде |
| Трекинг, ETA | Имитация | этапы двигает админ вручную; ETA = срок изготовления + 16–24 дня |
| Оплата, SMS, Google/Apple | Заглушки | тестовая карта, фикс. код 123456 |
| AR-примерка | Реально (на устройстве) | открытые модели лица и тела |

### Безопасность

- **Критично:** права на действия (провести платёж, сменить статус заказа, опубликовать товар) проверяются в браузере функцией `requireRole`. В продакше любой пользователь обойдёт это через консоль.
- **Высокий:** демо-режим включён по умолчанию (`DEMO_MODE` выключается только явно), есть запасной секрет сессий в коде, нет ограничения частоты запросов на вход по паролю.
- **Средний:** нет заголовков Content-Security-Policy и HSTS; пользователи хранятся в JSON-файле без блокировок записи.
- **Хорошо:** хэши паролей, проверка подписи cookie за постоянное время, роль берётся из серверного хранилища, а не из cookie; лимит попыток OTP; секреты — из переменных окружения.

### Качество

- Модели данных в `types.ts` продуманы и почти готовы стать схемой БД (заказ, платёж, инвойс, отправка, осмотр авто).
- Сервисы уже имеют форму API (асинхронные функции с кодами ошибок), поэтому замена их на HTTP-вызовы не сломает экраны.
- Риск: несколько страниц на 600–1 000 строк (`shop`, `auto`, `cargo`), бизнес-правила частично лежат в компонентах.
- Тесты проверяют сценарии целиком, но формулы (цена, вес, статусы) не покрыты юнит-тестами.

## Разрыв с новой концепцией

Переиспользуется примерно половина кода — почти весь фронтенд; все шесть движков и база данных пишутся с нуля.

| Часть | Решение | Почему |
| --- | --- | --- |
| Экраны, UI-кит, дизайн, переводы | Оставить | готово и протестировано; меняется только источник данных |
| Модели данных (`types.ts`) | Оставить и расширить | основа схемы БД; добавить источник, оффер, версии цен |
| Серверная авторизация (`auth.mjs`) | Перенести | логика верная, нужны БД, рейт-лимиты, настоящий SMS |
| Формула цены (`pricing.ts`) | Переписать как Price engine | структура верная, но ставки должны быть таблицами с версиями |
| Сервисы-имитации (`src/services`) | Заменить тонким HTTP-клиентом | сигнатуры функций сохранить, логику перенести на сервер |
| Сид-каталог и поставщики | Убрать из продакшена | вымышлены; оставить только для демо и тестов |
| Find / AI Buyer (имитация сходства) | Переписать | сейчас цифры не связаны с картинкой — это и есть «ложная точность» |
| CARGO ONE Score, «популярное» | Переписать | должны считаться из событий, а не задаваться вручную |
| Трекинг и ETA | Переписать как Logistics engine | модель этапов оставить, ETA считать по маршруту |
| AR-примерка, авто-раздел, VIP | Оставить как есть | независимы от новой концепции |
| Сборка-артефакт (клиентский вход) | Оставить как демо | не должна попадать в продакшен |

Чего в коде нет совсем: источники данных и их снимки, понятие «оффер» (один товар у нескольких продавцов), история цен, очереди фоновых задач, поисковый индекс, журнал действий админа, денежный реестр (ledger).

## Целевая архитектура

Один бэкенд-монолит с чёткими модулями (Node.js + TypeScript, чтобы переиспользовать типы и формулы фронтенда), PostgreSQL как единственный источник правды и фоновые обработчики для сбора и пересчётов. Текущий фронтенд остаётся и меняет только слой сервисов на HTTP-клиент.

## Source aggregation — сбор товаров из Китая

Агрегация строится на коннекторах с одинаковым интерфейсом, и каждый коннектор сначала проходит юридическую проверку: нелегальный источник не подключается.

### Источники по приоритету

| Тип | Примеры | Плюсы | Риски |
| --- | --- | --- | --- |
| 1. Продавцы загружают сами | кабинет поставщика, Excel/CSV-импорт | согласие и ответственность продавца | медленный рост каталога |
| 2. Официальные API площадок | 1688 Open Platform, Taobao Open Platform | стабильно, структурировано | нужны одобрение и, вероятно, китайское юрлицо — проверить |
| 3. Лицензированные посредники | дропшип-агенты, агрегаторы товарных фидов | быстрый старт, иногда с выкупом | цена доступа, зависимость от чужих условий |
| 4. Разовый импорт по ссылке | пользователь вставил ссылку в Find | сразу полезно для выкупа | только по запросу, без массового обхода |
| ✕ Массовый парсинг сайтов | 1688, Taobao, Pinduoduo | — | нарушает правила площадок, блокировки, юридический риск в КНР |

Условия доступа к официальным API я в этой работе не проверял; это первый пункт фазы 0.

### Как устроен коннектор

1. **Контракт.** У каждого коннектора три метода: `listChanged(since)`, `fetchOffer(id)`, `fetchSeller(id)`. Он ничего не нормализует — только забирает.
2. **Сырой снимок.** Каждый ответ сохраняется как есть (JSON + время + версия коннектора + хэш) в объектное хранилище. Можно пересчитать нормализацию без повторного запроса.
3. **Расписание.** Цена и наличие — часто (например, раз в 6–24 ч для активных товаров), описание и фото — редко; перед оплатой — обязательная свежая проверка цены.
4. **Вежливость.** Лимиты запросов на каждый источник, повтор с паузами, автоматическое отключение при всплеске ошибок.
5. **Здоровье.** Для каждого источника в админке видны свежесть данных, доля ошибок и число товаров, снятых из-за устаревания.

Товар, данные которого старше допустимого срока, показывается с пометкой «цена уточняется» и не может быть оплачен до проверки.

## Product normalization — один товар из многих объявлений

Главное решение: разделить **канонический товар** (что это за вещь) и **оффер** (кто продаёт, по какой цене, с каким MOQ). Сейчас в коде один `Product` жёстко привязан к одному поставщику, и сравнение «дешевле / дороже» невозможно честно.

### Сущности

| Сущность | Ключевые поля |
| --- | --- |
| `RawListing` | источник, id в источнике, сырой JSON, дата снимка, хэш |
| `CanonicalProduct` | категория, название EN/RU/TK, атрибуты по схеме категории, медиа, вес и объём, код HS |
| `Variant` | цвет/размер/комплектация, сопоставление с SKU источника |
| `Offer` | продавец, вариант, лестница цен по объёму (CNY), MOQ, наличие, срок отгрузки, свежесть |
| `AttributeSchema` | для каждой категории: обязательные поля, единицы, допустимые значения |

### Конвейер нормализации

1. **Извлечение полей** — по правилам для каждого источника: ценовые ступени, SKU, единицы (г, кг, см), атрибуты из таблицы характеристик.
2. **Классификация** — категория источника → таблица соответствия → наша категория; при низкой уверенности — модель на тексте и фото, далее очередь ручной проверки.
3. **Перевод** — машинный перевод заголовка и атрибутов ZH→RU/TK/EN с глоссарием терминов; оригинал хранится рядом. Пометка «переведено автоматически».
4. **Вес и объём** — из источника; если нет, оценка по категории с флагом `estimated`. Это критично для цены доставки, поэтому фактический вес со склада возвращается обратно в товар.
5. **Медиа** — копирование фото только там, где есть право; пересжатие в WebP, удаление дублей по перцептивному хэшу, фильтр водяных знаков и китайского текста на фото.
6. **Дедупликация** — кандидаты по текстовому и визуальному сходству (векторы), затем правила (совпадение атрибутов, разница веса ≤ 10%). Автослияние только при высокой уверенности, остальное — в очередь модератора.
7. **Контроль качества** — товар публикуется, только если заполнены обязательные поля схемы, есть вес и категория, и товар не в списке запрещённых к ввозу.

Уверенность каждого шага хранится; на витрине она не показывается процентами — иначе повторится нынешнее «сходство 98%».

## Seller verification — уровни доверия

Значок «Проверен» ставится только по записанным фактам проверки, а итоговая оценка продавца считается из событий заказов. Сейчас оба числа заданы вручную в демо-данных.

| Уровень | Что проверено | Что открывает |
| --- | --- | --- |
| 0 — Импортирован | ничего, только данные источника | показ с пометкой, заказ через выкупающего агента |
| 1 — Юрлицо подтверждено | лицензия (единый социальный кредитный код), сверка с госреестром, контактное лицо | прямые заказы, значок «Юрлицо» |
| 2 — Реквизиты и завод | банковский счёт на то же юрлицо, видеозвонок/фотоотчёт производства, сертификаты с сроками | оплата напрямую продавцу |
| 3 — Аудит на месте | визит партнёра или стороннего инспектора, фото + дата + адрес | значок VERIFIED, приоритет в выдаче |

Каждая проверка — это запись с документом, исполнителем, датой и сроком действия; истёкшая проверка снимает уровень автоматически. Как и в авто-разделе, нельзя писать «проверен» без записи.

### Динамическая оценка (CARGO ONE Score)

Считается раз в сутки за последние 90 дней из наших же событий: доля отгрузок в срок, расхождение веса и комплектации на складе, доля споров, время ответа, изменения цены после заказа. Пока заказов меньше порога (например, 10), оценка показывается как «мало данных», а не числом.

### Мониторинг и антифрод

- Смена банковских реквизитов → автоматический сброс до уровня 1 и ручная проверка (самый частый сценарий мошенничества с инвойсами).
- Имя получателя в инвойсе ≠ юрлицо продавца → платёж блокируется.
- Резкий рост заказов с низкими ценами у нового продавца → лимит на сумму до истории поставок.
- Документы и сертификаты с истекающим сроком → напоминание продавцу за 30 дней.

## Price engine — цена «под ключ» в TMT

Движок считает цену из версионированных таблиц и возвращает не число, а расчёт: каждая строка с источником ставки и пометкой «фиксировано / оценка». Структура нынешней формулы верная, меняется откуда берутся ставки.

```latex
P_{TMT} = \underbrace{p_{tier}(q)\cdot q \cdot fx_{CNY}}_{\text{товар}} + \underbrace{c_{CN}}_{\text{доставка по Китаю}} + \underbrace{L(route, kg_{ch})}_{\text{международная}} + \underbrace{D(HS, CIF)}_{\text{пошлины и налоги}} + \underbrace{F(user, method)}_{\text{комиссии}} + \underbrace{R}_{\text{буфер курса}}
```

| Компонент | Сейчас в коде | В новом движке |
| --- | --- | --- |
| Цена товара | одна цена за штуку | лестница по объёму из оффера, свежая на момент оплаты |
| Курс | фикс. 0,49 TMT/CNY и 3,5 TMT/USD | таблица курсов с датой и источником; курс платёжного канала, а не официальный |
| Доставка по Китаю | нет | по городу продавца и складу консолидации |
| Международная доставка | 28 / 62 TMT/кг, мин. 35 TMT | Logistics engine, по маршруту и объёмному весу |
| Пошлина и НДС | 10% на всё | по коду HS и таможенной стоимости; ставки только от таможенного брокера |
| Комиссии | 5% (VIP 3%) | правила по типу клиента, категории, способу оплаты |
| Буфер курса | нет | защита от колебаний между оплатой и расчётом с продавцом |

### Правила

- **Котировка (Quote).** При оформлении заказа расчёт замораживается с сроком действия (например, 30 минут) и сохраняется в заказе со всеми версиями тарифов. Потом можно точно объяснить любую цифру.
- **Оценка помечена.** Пошлина и доставка по оценочному весу — всегда «оценка»; после взвешивания на складе — доплата или возврат разницы.
- **Деньги в целых числах.** Хранить суммы в минимальных единицах (тенге, фэни), а не как дробные числа, как сейчас; округление один раз, в итоге.
- **Одна реализация.** Движок живёт на сервере; клиент показывает предварительную оценку тем же кодом, но итог всегда приходит с сервера.
- **Тесты.** Набор эталонных расчётов, сверенных с бухгалтерией; любая правка тарифов прогоняется через них.

## Logistics engine — стоимость, срок и статус доставки

Движок отвечает на три вопроса: сколько стоит перевозка, когда придёт и где сейчас. В текущем коде есть только модель этапов и консолидация; тарифы и сроки заданы константами.

### Модель

- **Узлы:** продавец → склад консолидации в Китае (например, Иу, Гуанчжоу, Урумчи) → погранпереход → таможня ТМ → склад в Ашхабаде → пункт выдачи или курьер.
- **Маршрут** = последовательность плеч (ж/д, авто, авиа), у каждого — перевозчик, тариф, делитель объёмного веса, дни отправки, транзитное время (минимум / медиана / 90-й перцентиль).
- **Тарифная сетка:** цена за кг или м³ по диапазонам, надбавки за тип груза (батареи, жидкости, хрупкое, бренды), минимальная партия, срок действия ставки.
- **Объёмный вес:** сейчас делитель 167 кг/м³ применяется ко всем видам транспорта. В движке делитель берётся из тарифа перевозчика для каждого плеча.

### Функции движка

| Функция | Вход | Выход |
| --- | --- | --- |
| `quote` | список позиций (вес, объём, тип груза), город продавца, город получателя | 2–3 варианта: цена, срок (диапазон), запреты |
| `consolidate` | несколько посылок на складе | план упаковки, экономия, дата ближайшей отправки |
| `eta` | текущий этап + история по маршруту | диапазон дат с уверенностью |
| `track` | события перевозчика и склада | нормализованный статус CARGO LINE |

### Источники событий

1. Сканер на наших складах: приёмка, фактический вес и габариты, фото товара — самые ценные данные для цены и для оценки продавца.
2. API или файлы от перевозчиков и карго-партнёров.
3. Ручной ввод оператором — как сейчас в админке, но с журналом и автором каждого изменения.

ETA учится на фактических сроках: через несколько сотен отправок медиана и 90-й перцентиль по каждому плечу заменяют стартовые оценки партнёров.

## Trend engine — что показывать первым

Тренды считаются из двух разных рынков: спрос в Туркменистане (наши события) и движение в Китае (данные источников). Сейчас «Популярное в Туркменистане» — случайное число из демо-данных; до запуска движка этот блок нужно переименовать или скрыть.

| Сигнал | Откуда | Вес на старте |
| --- | --- | --- |
| Покупки и оплаченные заказы | наша БД | высокий |
| Добавления в корзину, избранное, примерки | события клиента | средний |
| Поиски без результата, запросы Find и AI Buyer | журнал поиска | средний — подсказка, что добавить в каталог |
| Просмотры карточек | события клиента | низкий |
| Продажи / рейтинг на площадке источника | сырые снимки | низкий, для новых товаров без истории |
| Падение цены у продавца | история офферов | для подборки «Снижение цены» |

### Как считается

- **Скорость, а не объём.** Тренд = рост сигнала за 7 дней относительно среднего за 28, со сглаживанием для малых чисел (иначе два заказа вместо одного — «+100%»).
- **По городам и сегментам.** Ашхабад, Мары, Туркменабад…; розница и бизнес считаются отдельно.
- **Выход:** ранжированные списки для главной (те же карусели, что сейчас), подсказки для поиска, список «что искали, но не нашли» для закупки и продавцов, кандидаты для совместных покупок.
- **Расписание:** пакетный пересчёт раз в час в отдельную таблицу; витрина читает готовый результат. Потоковая обработка на старте не нужна.

### Защита от манипуляций

- Один пользователь = один голос в сутки по товару; действия продавца со своими товарами не считаются.
- Отменённые и возвращённые заказы вычитаются.
- Платное продвижение в выдаче всегда помечается «Реклама» и не влияет на трендовые списки.

## Internal marketplace — заказ, деньги, споры

Покупатель видит одну витрину и платит CARGO ONE одним платежом, а внутри заказ делится на подзаказы по продавцам. Кто юридически продавец для покупателя — CARGO ONE (модель выкупа) или китайский продавец (чистый маркетплейс), решает владелец с юристом (см. открытые вопросы); архитектура ниже работает для обеих.

### Жизненный цикл заказа

1. **Котировка** (Price engine) → оплата покупателем → деньги на холде.
2. **Подзаказ продавцу** → подтверждение цены и наличия за N часов; иначе замена оффера с согласия покупателя или возврат.
3. **Оплата продавцу** через лицензированного партнёра (как и сейчас принципиально: никакого P2P-обмена).
4. **Приёмка на складе в Китае** → фото, вес, проверка комплектации → доплата / возврат разницы по весу.
5. **Консолидация и отправка** (Logistics engine) → таможня → выдача.
6. **Закрытие:** окно спора (например, 7 дней), затем финальный расчёт и события для оценки продавца и трендов.

Каждый переход статуса — серверная команда с проверкой роли и допустимости перехода (конечный автомат), а не запись из браузера, как сейчас.

### Деньги

- **Реестр двойной записи (ledger):** счета покупателя, холда, продавца, комиссии, логистики, курсовой разницы. Баланс считается из проводок, проводки не редактируются — только сторнируются.
- **Идемпотентность:** каждый платёжный запрос и вебхук с ключом, чтобы повтор не списал дважды.
- **Сверка:** ежедневно с выписками платёжных партнёров.

### Роли и кабинеты

Роли из текущего кода (покупатель, бизнес, поставщик, админ) сохраняются. Добавляются операторские роли с узкими правами: модератор каталога, верификатор продавцов, склад, финансы, поддержка. Все действия операторов идут в журнал аудита.

## Данные, хранилище, поиск, наблюдаемость

На старте достаточно PostgreSQL + Redis + объектного хранилища; отдельный поисковый движок нужен, когда каталог перевалит за сотни тысяч офферов.

| Хранилище | Что там | Почему |
| --- | --- | --- |
| PostgreSQL | пользователи, продавцы, канонические товары, офферы, заказы, ledger, тарифы, события отправок | транзакции для денег; JSONB для атрибутов; полнотекстовый поиск и pgvector для старта |
| Объектное хранилище (S3-совместимое) | сырые снимки источников, фото, документы продавцов, инвойсы | дёшево, неизменяемо, сроки хранения |
| Redis | очереди задач, лимиты, кэш котировок, сессии | быстро; всё восстанавливаемо из PostgreSQL |
| Поиск (позже: OpenSearch или Meilisearch) | индекс канонических товаров на 3 языках | только когда PostgreSQL перестанет справляться |

### Поиск и Find

- Текст: токенизация RU/TK/EN + синонимы и транслит («кросовки», «krossowka», «sneakers» → одна категория).
- Фото: векторное представление изображения и поиск ближайших товаров — замена нынешней имитации по имени файла.
- Ссылка: определить источник и id → найти существующий оффер или сделать разовый импорт через легальный коннектор.

### Наблюдаемость

- Структурные логи с id запроса, метрики по каждому движку, алерты: источник не обновлялся N часов, расхождение сверки ledger, рост споров.
- События продукта (поиск, карточка, корзина, оплата) — одна схема для аналитики и для Trend engine.
- Резервное копирование PostgreSQL с восстановлением на точку во времени и проверкой восстановления раз в месяц.

## Безопасность и комплаенс

Всё, что связано с деньгами, ролями и данными продавцов, решается на сервере; браузер только показывает. Юридические пункты ниже — вопросы для юристов в КНР и Туркменистане, а не готовые ответы.

### Технические меры

- Проверка прав на каждом серверном методе (роль + владение объектом: продавец видит только свои заказы).
- Демо-режим выключен по умолчанию; сервер не стартует без секрета сессий.
- Лимиты запросов на вход, OTP, платежи и поиск; CSP, HSTS, CSRF-защита для изменяющих запросов.
- Двухфакторный вход для операторов и админов; разделение обязанностей (тот, кто меняет реквизиты, не одобряет платёж).
- Документы продавцов и инвойсы — в закрытом хранилище с временными ссылками; проверка файлов на вирусы при загрузке.
- Журнал аудита для всех изменений тарифов, цен, статусов продавцов и ролей.

### Вопросы для юристов

| Тема | Что выяснить |
| --- | --- |

| Персональные данные | данные контактных лиц продавцов (PIPL в КНР), данные покупателей по законам Туркменистана, место хранения |

| Ответственность перед покупателем | модель выкупа или агентская схема, возвраты, гарантия |

## Риски и открытые вопросы

Самый большой риск — не технический: без легального источника данных и платёжного канала в CNY концепция не работает при любой архитектуре.

| Риск | Влияние | Что делаем |
| --- | --- | --- |
| Нет официального доступа к API площадок | каталог растёт медленно | старт с продавцами-партнёрами и посредниками; импорт по ссылке по запросу |
| Цена у продавца изменилась после оплаты | убыток или недовольный клиент | свежая проверка перед оплатой, срок котировки, буфер, правила доплаты |
| Ошибка веса и пошлины | итоговая цена не совпадает с обещанной | пометка «оценка», фактический вес со склада обратно в товар, тарифы от брокера |
| Мошенничество с реквизитами продавца | потеря денег | уровень 2 для прямых выплат, автосброс при смене счёта, двойной контроль |
| Перегруженная ручная модерация | товары и продавцы ждут неделями | пороги автоматического одобрения, очереди с приоритетом по спросу |
| Переписывание вместо запуска | сроки растягиваются | фронтенд не трогаем, меняем только слой сервисов; фазы с чёткими критериями |

## Уточнения после проверки кода в W1 (9 октября 2026)

Этот файл — копия аудита W0 из документа Claude Docs. При работе над W1 код проверен повторно; ниже — поправки.

- **CSRF.** Базовая защита уже есть: сервер принимает только `GET`/`POST`, для `POST` требует `Content-Type: application/json` и отклоняет запросы с чужим заголовком `Origin` (`server/server.mjs`). Пункт «CSRF-защита» в разделе «Технические меры» следует читать как *усиление* (токены, `SameSite=Strict` для админки), а не как отсутствующую защиту.
- **`.env.example` существует.** Ошибка была в README: он называл переменную `SESSION_SECRET`, а сервер читает `AUTH_SECRET`. README исправлен, в `.env.example` добавлены переменные каталога (`DB_FILE`, `CATALOG_DEMO_SEED`, `CATALOG_STALE_HOURS`, `IMAGE_HOSTS`).
- **Публикация товаров** больше не проверяется только в браузере: в серверной сборке создание, правка, публикация и архивирование товаров идут через `/api/catalog/manage/*` с проверкой роли и владельца на сервере. Платежи, заказы и статусы груза по-прежнему локальный мок — это остаётся критичным пунктом для следующих этапов.
- **Тесты формул.** Ядро цены теперь покрыто юнит-тестами (`tests/pricing.test.mjs`).
